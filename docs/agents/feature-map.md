# Feature-Karte (aus CLAUDE.md ausgelagert)

## Project Overview

Orkumo is a React-based workspace for agentic development. It scans the directories configured in the admin panel as a project registry (projects open in Code mode, `/code?path=`); it no longer starts, stops or analyzes apps (issue #143). The registry lists git main checkouts only (a `.git` directory; `scannerService.js` `gitRootInfo`). Linked worktrees, wherever they live, belong to their main repo (`worktrees`, from `.git/worktrees/*/gitdir`); folders without git are no projects. User overrides in `settings.json`, keyed by project id: `archived` (disabled, left out of `GET /api/apps`), `customNames`, `projectMerges` {source: target}, `customProjects` [{id, name, paths}], applied by `applyProjectOverrides`; `GET /api/projects` lists every project with state for the settings UI (`components/ProjectsSettings.tsx` in the admin panel, opened at a project by the window event `orkumo:project-settings` / group menu "Project settings…"). Routes: `PUT /api/settings/archive|name/:id`, `PUT /api/settings/project-merge/:id {into}`, `POST|PUT|DELETE /api/settings/projects/custom[/:id]`. Context members that name no project are ignored, never removed.

Activity bar (#184, `components/ModeSwitcher.tsx`): narrow vertical column at the left edge of the AgentsView, like VS Code: Agents · modes of loaded modules (e.g. Workflows, #165) · Board · Issues · Pull Requests · Code, settings gear at the bottom; the route is the state. The AgentsView header starts with the robot and the split button [New task | ⌄] (`components/AgentsView/NewTaskButton.tsx`: agent, chat, issue in the dropdown). The robot opens the context dashboard (`/dashboard?scope=context`), the rocket in the title bar the global one (`/dashboard`); the title bar's right edge opens the command palette (Cmd/Ctrl+P).

Main agent (#252): `components/AgentsView/MainAgentDialog.tsx` (peek panel on the background session named `agentView.mainAgent.name`, default `main-orchestrator`), opened by the title bar button (window event `orkumo:main-agent`) or the palette from every view; `server/services/mainAgent.js` respawns that session when it is stopped (`keepAlive`, checked with every agents poll, at most every 5 min, no prompt).

Orchestrators (`server/services/orchestratorService.js`, templates and CLI in `server/orchestrator/`, copied into `dist-server/orchestrator` by `scripts/bundle-server.js`): sessions listed in `agentView.orchestrators` (row id, transcript uuid or pane id; `isOrchestrator` / `withOrchestratorSessions` in `utils/agentSessions.ts`) sit in a pinned Orchestrators group above Favorites in every grouping and carry a badge on their card. They are marked from the row menu (a briefing is typed into the pane or sent as a reply to the job, `GET /api/orchestrator/workspace`) or started with "New orchestrator" in the New task dropdown (`POST /api/orchestrator/start`: default harness as pane `orch-<uuid>` in the workspace, `orkumo` on PATH, `ORKUMO_CLI` set). The server creates `<data>/orchestrator/` at every start (AGENTS.md + CLAUDE.md link, `.claude/settings.json` that denies Task/Agent and blocks edits outside the workspace with a hook running `orkumo guard`, the skill under `.claude/skills` and `.omp/skills`); the CLI (`orkumo`, `orkumo.mjs`, `orkumo.json`) lives outside it in `<data>/orchestrator-bin/`, all generated files read-only (0444/0555), so an orchestrator cannot rewrite its pre-approved CLI. The `orkumo guard` hook (Edit/Write/NotebookEdit/Bash) allows writes only to `NOTES.md` and plain files inside the workspace (Bash detection best effort). NOTES.md is never overwritten; `getAllowedDirectories` accepts the workspace. The `orkumo` CLI (`orchestrator-bin/orkumo.json` holds the API address and token file; the token goes only to loopback `apiUrl`s, env overrides included) uses `GET /api/orchestrator/overview` (`?all=1`, `?text=0`), `/projects`, `/agents/:id/transcript?last=N`, `POST /api/orchestrator/panes` (omp/claude pane `work-<uuid>` in a project) and the existing dispatch, reply, pane message and stop routes.

Quick window (#251, `components/QuickWindow.tsx`, desktop app): Enter starts the default harness in ~ as agent pane `quick-<uuid>` (`server/services/quickAgent.js`, `POST /api/agents/quick`; Claude Code with `--session-id`, omp's id from its session store row naming the pane) and shows its transcript through a UI view; follow-ups go through `POST /api/agents/panes/:paneId/message` (`typeIntoPanePty`). Cmd+Enter sends the pane id to the main window, which opens the pane once its stand-in row is listed (reattach); hiding stops the pane.

Fixed projects (#253, `fixedProjects` in `hooks/useRailPreferences.ts`, per context): directories whose group in the Project grouping exists without sessions (`groupSessions` option `fixedProjects`, `SessionGroup.fixed`); set from the group menu or the palette command "Add fixed project…". Fixed projects are projects only: the picker lists the registry, and a stored directory that no project contains is ignored. In the Project grouping each session's project is the server's `AgentContext.projectId` (repo root, else worktree / cwd, against detected and custom projects); the client maps merged ids to their target and puts sessions without a project into one `project:none` group, "No project".

Rail filter row (`AgentFilterBar` in `components/AgentsView/AgentSummaryBar.tsx`): one line with the grouping (`GroupingPicker` in `ProjectsRail.tsx`, shows the current grouping, hover lists the others), sort, filter chips toggle, one search button (Cmd/Ctrl+K; in a terminal off macOS Ctrl+Shift+K) whose panel narrows the agents by text and lists the matching PRs and issues as link filters, and `FoldButtons` (`ProjectsRail.tsx`): toggles that collapse / expand all groups and all agent cards' details.

Terminal links (`AgentTerminal.tsx`): Cmd/Ctrl-click on a URL follows the link setting, Cmd/Ctrl+Shift-click opens the system browser (also for app anchors, `utils/links.ts`). Cmd/Ctrl-click on a file path opens it in VS Code in the window of the pane's project (`POST /api/files/open-in-editor`, git root above the pane's cwd, `-g file:line:col`); with Shift its default macOS app (`POST /api/files/open`); folders open in Finder.

Chats mode (`/chats`, #280, `components/ChatHistoryView/ChatHistoryPage.tsx`, `server/services/chatHistoryService.js`): lists claude.ai and ChatGPT conversations in the AgentsView rail column (prop `railOutlet`, context in `components/AgentsView/railOutlet.ts`; below `md` the list stays inside the page). In the desktop app `electron/chatSync.js` (main process, IPC `chat-sync` / `chat-sync-progress`, preload `electronAPI.chatSync`) reads them with the built-in browser's session (`persist:browser-preview`) from allowlisted, undocumented endpoints, incrementally by last activity, and posts batches to the loopback-only `POST /api/chat-history/ingest` (media type `application/vnd.orkumo.chats+json`); its stop point comes from `GET /api/chat-history/sync-state`. Cookies and tokens never leave the main process. The store keeps imported and synced conversations through one `upsert`: append-only JSONL in `<data>/chat-history/conversations.jsonl` where the last line of an id wins, compacted when stale lines outweigh live ones, `sync-state.json` next to it; search on a lower-cased in-memory copy, topics from shared title words (`assignTopics`). Web mode and remote clients use the data-export import (`POST /api/chat-history/import {path}`, overflow menu). "Continue in Orkumo" opens the chat composer

Chats as a desktop chat app (DevHub-pro#19): "New chat" (rail header of /chats, the quick window's prompt, the chat composer's folder choice "Chats (no project)") runs the agent in `<data>/chats` (`server/services/orkumoChats.js` `chatsDir`, created by `GET /api/agents/repos` → `chats`, an allowed working directory in `getAllowedDirectories`, so `claude --bg` works there unlike in ~); that folder marks a session as a chat. The history scans the transcripts of every session that ran there (Claude's project folder of it, omp/pi session folders whose `session` record names it, codex rollouts whose `session_meta.cwd` names it; `createOrkumoChatScanner`, at most every 3 s on list/get, only changed files) and stores them as source `orkumo` (`orkumo:<harness>:<sessionId>`), so list, counts and search cover them; "Open in Agents" attaches the running pane or resumes the session (router state `openChat`). Pin, rename, folder, archive: local marks in `<data>/chat-history/meta.json` (`setMeta`, `PATCH /api/chat-history/meta`, atomic write; a local title replaces the provider's in list and search); archived ones only with `archived=true`. Export: Markdown download (`conversationMarkdown`, `utils/chatHistory.ts`). "Continue in Orkumo" stores the whole conversation via `POST /api/agents/files` and keeps the prompt under `promptLimit(harness)` (`config/limits.js`: dispatch 20 000, PTY 1 500) with room for the user's addition. Attachments: images plus PDF, text, code (`ATTACHMENT_EXTENSIONS`, 20 MB, content checked; `server/services/agentFiles.js`, `<data>/agent-files/<uuid>/<name>`, `[File: <path>]`). Model per agent / chat: Claude Code via the dispatch `model`, Codex/omp/pi as `--model <name>` before the prompt (`HARNESS_MODEL_SUPPORT` / `MODEL_NAME_RE` in `config/harnesses.js`, mirrored by `HARNESS_MODEL_FLAG`). Fenced code in `ChatMarkdown` is highlighted by `utils/highlight.ts` (no dependency).

Issues mode (`/issues`, `components/IssuesView/`, `server/services/issueListService.js`, route `GET /api/issues?context=&state=open|closed&refresh=1`): issues of the active context's repos (origin remotes of its apps, `appIds: null` = all, plus `repo:` board slices), read per repo via `gh api graphql`, so issues off the board are listed too (`onBoard` flag). Filters, grouping and sorting in the URL (`utils/issueQuery.ts`); a row opens the issue modal.

The dashboard (`/dashboard`, context variant filtered to the active context's project paths via `utils/projectScope.ts`) shows:

- Agent table (`components/AgentOverview.tsx`, `utils/agentTable.ts`, buckets from `utils/agentOverview.ts`): stat filters (running / needs input / working / done / cache expires < 10 min / compaction needed), search, grouping, actions jump / stop / restart / rename / delete with an in-app confirm dialog
- Sessions card (`components/UsageView/SessionsCard.tsx`, `GET /api/usage/sessions?days=`): last 7 days, tabs newest / most tokens / longest (first to last answer)
- Compact usage card linking to the usage page
- Tool versions (`server/services/toolVersionsService.js`, `GET /api/system/versions`): node, npm, git, docker; on the context dashboard also the Node version each project pins (.nvmrc, .node-version, engines.node)

Usage page (`/usage`, `components/UsageView/`, `server/services/usageService.js`, route `/api/usage?days=1..90`):

- Tokens per day, model and provider (input, output, cache read, cache write) for Claude Code, each Codex account and MiniMax, read from local session logs (`~/.claude/projects`, `$CODEX_HOME/sessions`)
- Plan limits (5h / week): Codex from the newest `rate_limits` event (also outside the window for idle accounts; a window past its reset counts as 0 %); Claude from a fresh statusline snapshot (`scripts/claude-rate-limits-tap.sh`), else live from the endpoint Claude Code's `/usage` calls with the subscription login (token from keychain / `.credentials.json`, server-side only, 5 min cache, no refresh), else `~/.claude.json`; missing source shows "Limit unbekannt", a source without a 5h window shows no 5h bar, snapshots older than 1 h are marked "veraltet" with their age; back button to the previous view
- `scripts/verify-usage.mjs --days 30` re-sums the same logs independently and diffs per day and provider

  - `components/AgentsView/` - list, dispatch input, peek panel, attached sessions in tabs / tiled panes
  - `server/services/agentService.js` - wraps the `claude` CLI (`--bg`, `agents --json`, `logs`, `stop`, `respawn`, `rm`, `daemon`) and `~/.claude/jobs` state; routes under `/api/agents/*`
  - Live list: `server/services/agentRefresh.js` watches the session stores (jobs, sessions, omp) and runs `claude agents --json` only after a change (debounced, ≤ 1 per 2.5 s) plus a 60 s reconcile, while an SSE client (`/api/agents/stream`) is subscribed; client polls go through `utils/visiblePoll.ts` and pause while the page is hidden; contexts (`useAgentContexts`) refetch on session state/turn changes
  - `utils/agentInput.ts` (dispatch syntax) and `utils/agentSessions.ts` (grouping) are pure and unit-tested
  - Interactive terminal sessions no Orkumo pane runs (no `paneId`; any harness: started elsewhere, often by another agent, or ended) are hidden in the rail unless the footer switch "Interactive sessions" is on (localStorage `devOrbitAgentInteractive`)
  - Claude app sessions (`kind: 'app'`, `server/services/appSessions.js`): interactive sessions whose `~/.claude/sessions/<pid>.json` has a `bridgeSessionId`; title, origin and status come from `api.anthropic.com/v1/sessions/<id>` with the subscription login (server-side, cached 60 s), they open on claude.ai
  - Oh My Pi sessions (`server/services/ompSessions.js`, harness #195): rows `omp-<uuid>` from `~/.omp/agent/sessions/*/*.jsonl` (running ones plus those written in the last 7 days), running = an `omp` process holds the file (lsof) or its terminal's `~/.omp/agent/terminal-sessions/<tty>` names it; `paneId` links a row to the Orkumo terminal pane that runs it; opening resumes with `omp -r <uuid>`. omp has no attach: a session running in another terminal is taken over (`POST /api/agents/omp-<uuid>/stop` SIGTERMs the process holding it, then the pane resumes it)
  - omp working detection (`server/services/ompSessions.js`): a running session (lsof holder; an open subagent transcript `<stem>/<agent>.jsonl` counts for its parent `<stem>.jsonl`) is working while the end of its file shows an open turn (`turnSignal`/`readTurnState`: assistant `toolUse`, user/toolResult, `tool_execution_start`, a turn-starting `custom_message`; idle after `stop|aborted|error|length` or `session_exit`; title, usage and reminder records ignored), while a subagent written after the parent's last write has an open turn, or while its Orkumo pane printed within 3 s (`ptyService` `outputAt` / `activity` event, `agentPanes()` → `{ paneId, active }`). Claude terminal rows: busy → working, waiting → needs-input
  - Refresh (`agentService.subscribe`): omp store changes and pane `activity` events run an omp-only refresh merged with the cached Claude part (no `claude agents --json`); the full refresh lists Claude and omp in parallel and keeps the last Claude rows if the CLI fails
  - UI view (#189; `components/AgentsView/Chat/ChatPane.tsx`, client reducer `utils/chatEvents.ts`): every agent runs as its TUI in a terminal pane (PTY); the UI view is a second rendering of that pane, so switching terminal ↔ UI (pane header buttons "UI view" / "Terminal view", state per pane in `useAgentWorkspace` `views`, localStorage `devOrbitPaneViews`) never starts or stops a process. The terminal stays mounted (invisible) under the UI view; messages are pasted into its PTY (`typeIntoPane` in `AgentTerminal.tsx`), Stop sends Esc, prompts are read from its screen. `server/services/chatService.js` tails the transcript (`POST /api/agents/chat/view` with harness `claude`|`omp`|`pi`, sessionId, cwd; replay buffer, watchers, orphan timer stops an unwatched view), readers in `server/services/chatTranscripts.js` translate to Claude Code's stream-json event shapes: Claude `~/.claude/projects/<slug>/<uuid>.jsonl`, omp/pi session jsonl (`~/.omp|.pi/agent/sessions/<dir>/<ts>_<uuid>.jsonl`). A pane finds its session id from its args or the server row that names it (`paneId`, also for Claude terminals). "New chat" starts the same agent as "New agent", opened in the UI view; "Open agents in" (settings) picks the view a pane opens in. opencode and codex have no transcript reader: terminal only
  - Chat streams: all UI views of a window share one SSE per agent target (`subscribeToChat` in `services/agentsApi.ts`; `GET /api/agents/chat/events?client=`, then `POST|DELETE /api/agents/chat/:chatId/watch` {client, sub}; events `ready`, `watch` {sub} before each replay, `message` {sub, event}). Never one connection per view: Chromium allows 6 HTTP/1.1 connections per host, and with 5 views plus the agents stream every fetch (context switch, delete, …) queued forever
  - UI view `/` picker: Claude views combine `CLI_BUILTINS` + `CLI_INTERACTIVE_BUILTINS` (`claudeBuiltins.js`) with `listSlashCommands` (`agentService.js`: project `.claude` folders up to the git root, user commands and skills with symlinks followed and `skills/synced/*/*`, skills and commands of enabled plugins as `plugin:name`). omp views get `OMP_TUI_BUILTINS` at once, then `listOmpCommands` (`ompCommands.js`: short-lived `omp --mode rpc --no-session --config <skills overlay>` answering `get_available_commands`, cached per real binary path and cwd for 5 min; fallback snapshot + Claude skills as `skill:<name>`). pi views get no list. Regenerate both built-in snapshots when omp or Claude Code changes version
  - UI view answers: `groupAnswers` in `utils/chatEvents.ts` merges the assistant messages of one turn into a `ChatAnswer` (`ChatItemView` in `ChatMessages.tsx`). Durations come from Claude's `turn_duration` records (sent as `result` events) or, for omp/pi, from the `ts` on prompt and turn-end events. File paths in markdown resolve against `ChatFileContext` (the pane's cwd) and open via `utils/openFile.ts`
  - Artifacts of a UI view (`server/services/chatArtifacts.js`, `components/AgentsView/Chat/ChatArtifacts.tsx`): `chatService` records every file tool call of the tail in `artifactLog`, plus omp/pi `local://` documents from `<session file without .jsonl>/local`. `GET /api/agents/chat/:chatId/artifacts` → `{artifacts:[{path,name,kind,action,size,mtime,exists}]}`; `GET /api/agents/chat/:chatId/artifacts/content?path=` serves text only for listed paths inside the project dirs or the session's document folder (symlinks resolved), up to 1 MB (404/403/413/415 otherwise)
  - Status line of a UI view (`/api/agents/chat/:id/status`, `chatStatus.js`): git, prompt cache and context from a Claude transcript, Claude's plan limits for Claude models. PR links: Claude jobs report theirs, every other session gets the open PRs of its branch (`withBranchPullRequests` in `utils/agentSessions.ts`); board issues follow from those PRs
  - omp sessions Orkumo starts (terminal panes) get the user's Claude skills: `server/services/ompSkills.js` writes an omp `--config` overlay (`skills.enableClaudeUser`, `enabledProviders` + `claude-plugins`, merged with the user's own providers), so omp loads `~/.claude/skills` and the enabled Claude plugins and lists them as `/skill:<name>`; the UI view's `/` picker lists every command (no cap)
  - Card details (issues, PRs, servers) open only with the chevron at the card's left edge and stay open (`expandedSessions`); clicking a card only selects it; the filter row's fold toggle opens / closes all
  - Panes of a tab form a split tree (#212, `SplitNode` in `utils/agentWorkspace.ts`, rendered as nested `react-resizable-panels` groups in `AgentWorkspace.tsx`): a pane dropped on a pane edge halves only that pane, closing collapses the parent, the layout buttons rebuild the tree flat. Slot ids keep the panels of untouched panes (mounted, same size); `migrateWorkspace` reads the flat `panes` + `layout` shape from before
  - A pane's xterm and PTY socket live in a registry in `AgentTerminal.tsx` (`paneTerminals`), not in the component: splitting / unsplitting remounts the pane and takes them back; an unmounted pane is released after 2 s. Without this a remount started a new PTY and ended omp and shell panes
  - Agent panes outlive pane, page, server and Electron: each agent PTY (`agent-<pane>-<ts>`, all but `claude attach`) runs in its own detached holder process (`server/services/ptyHolder.js`, client `heldPty.js`; Unix socket `<data>/pty/<hash>.sock`, newline-delimited JSON, output backlog). Closing a pane or tab or reloading only detaches; a new socket for the pane reattaches (`openAgentPty` in `ptyService.js`); a starting server reconnects to the holders still running (`restoreHeldPtys`, before it listens). Server rows name the pane (`paneId`), so the rail lists the detached agent, `openPlan` returns `reattach`, and after a reload `paneStandIns` in `AgentsView.tsx` rebuild the pane. Row menu "Stop" ends it (`POST /api/agents/panes/:paneId/stop`). Shell panes are PTYs of the server and end with their socket. Docker mode proxies to pty-host, which still ends a PTY with its socket. `scripts/bundle-server.js` bundles `ptyHolder.js` next to `index.js`

## Desktop updates

- `electron/updater.js` picks the mode (off/install/swap/notify), runs the checks (5 s, then every 6 h, while settings `autoUpdate` ≠ false) and sends status over IPC `update:status`; the renderer reads it via `window.electronAPI.updates` (`getStatus`/`check`/`install`/`onStatus`) in `components/UpdatesSection.tsx` (`UpdatesSection` in AdminPanel, `UpdateBanner` in App.tsx).
- `electron/selfUpdate.js`: macOS self-update without a Developer ID: version/channel order, `releases.atom` + `*-mac.yml` parsing, sha512-verified download, ditto staging, and the detached `updates/swap.sh` that swaps the bundle by rename with rollback (log `updates/swap.log` under userData).
- `electron/menu.js` builds the application menu as plain data; Settings… sends IPC `open-settings`, which App.tsx answers with `setAdminPanelOpen(true)` (the renderer's own Cmd+, shortcut in `hooks/useKeyboardShortcuts.ts` also fires from text fields and terminals).
- `scripts/release/build-local.mjs` stamps local electron-builder runs `<version>-rc.<N>.dev.<sha>` (N = highest known rc, so an older release is never offered as update); `test/selfUpdate.e2e.test.js` and `scripts/review/126/e2e-mac.sh` (case `swap-rc1-to-rc2`) prove the update path against a local fake GitHub.

## Exposure

- The API listens on `127.0.0.1` (`server/index.js` `startServer`); Docker on every interface; `DEVORBIT_LISTEN_HOST` opts in to another address. Remote access goes through `tailscale serve` with the pairing token (`remoteAccess.js`).
- Text typed into agents (`typedTextSchema` in `server/index.js`, `typeIntoPanePty`) carries no control characters besides tab/newline; start prompts that become CLI arguments follow `--` and must not start with `-` (`startPromptSchema`, `quickAgent.js`).
- Requests with Origin `null`/`file://` (or no Origin but `Sec-Fetch-Site: cross-site`) reach the API only with the per-launch renderer secret that `electron/rendererSecret.js` adds to the main and quick windows' top-frame requests (server env `DEVORBIT_RENDERER_SECRET`, removed from `process.env` after reading), or with the pairing token; the built-in browser and frames inside the app never get it. Chat history routes except ingest require the renderer secret, a local request without Origin, or a loopback page on the server port or `VITE_PORT`. Proof fixture: `scripts/review/renderer-secret/fixture-main.mjs`.
